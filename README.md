# DDQ-APUF Reproduction and HMAC-Secured Authentication

A Verilog reproduction of the DDQ-APUF (delay difference quantization arbiter PUF) design, a successive-approximation (SAR) quantizer extension, regression-attack experiments against the exposed response, and a synthesizable SystemVerilog **HMAC-SHA-256 authentication wrapper** that hides the raw PUF response.

## The key security result

The tolerance `d` applies to the raw numerical DDQ response. At `d=3`, the regression attacker passes essentially 100% of the exposed-response tests in our model. This is the insecure baseline.

The protected interface does not use a DDQ tolerance. It requires an exact match of all 64 HMAC tag bits. On tags generated by the SystemVerilog RTL:

| training transactions | attacker per-bit accuracy | exact 64-bit forgeries |
|---:|---:|---:|
| 100 | 49.923% | 0/2000 |
| 300 | 50.078% | 0/2000 |
| 1,000 | 49.979% | 0/2000 |
| 3,000 | 49.986% | 0/2000 |
| 10,000 | 50.104% | 0/2000 |

Approximately 50% per-bit accuracy is random guessing; it is not 50% authentication success. A forgery is accepted only when all 64 bits match. No complete forgery succeeded in the measured RTL tests. The ideal blind-guess probability for one attempt is `2^-64 = 5.42e-20`.

The replay experiment also accepted `0/2000` previously observed tags when the same challenge was paired with a fresh nonce.

These numbers are reproduced by the commands in [Run the C3 pipeline](#c3-rtl-generated-dataset-and-attack) below, and re-checked on every push by GitHub Actions.

## What is a nonce?

A nonce is a fresh number used once. The verifier sends a new 64-bit nonce with each 32-bit challenge. The authenticator calculates:

```text
tag = HMAC-SHA-256(secret_key, challenge || nonce)[255:192]
```

If an attacker records a valid old tag, that tag is tied to the old nonce. A new nonce changes the HMAC input and therefore the expected tag, so replaying the recording fails. The verifier must generate nonces that do not repeat and must reject reused or stale nonces.

## Additions beyond the paper

- A controlled interface that does not expose raw DDQ, SAR, or individual-core responses.
- A 256-bit secret-key boundary intended to receive a key reconstructed from stable PUF measurements.
- HMAC-SHA-256 over `challenge || nonce`, truncated to a 64-bit tag.
- Nonce-based replay protection.
- Volatile key storage, explicit key clearing, and an error when authentication is attempted before a key is loaded.
- A synthesizable iterative SHA-256 compression core and fixed-message HMAC controller.
- Independent HMAC test vectors and a self-checking top-level RTL testbench.
- An RTL-generated dataset and a with/without-protection regression attack.
- A SAR quantizer experiment: 7 arbiter evaluations and 127 levels versus the paper's unary 13 evaluations and 14 levels.
- Delay-scale/temperature-model experiments and a mean-versus-median combiner experiment.

## Requirements

- [Icarus Verilog](https://steveicarus.github.io/iverilog/) 12 (or Vivado XSim, for the `run_xsim` scripts)
- Python 3 with `numpy` and `matplotlib`: `pip install numpy matplotlib`

## Run it

### A. PUF simulations (paper design, SAR extension, temperature sweep)

```sh
./scripts/run_icarus.sh                      # Linux / WSL / macOS, about 2 minutes
scripts\run_xsim.bat                         # Windows, from a Vivado Tcl Shell
python3 plot_ddq.py logs/run.log logs/run_sar.log logs/run_temp.log
```

Look for `TEST PASSED` in each log.

### B. Python models

```sh
python3 ddq_regression_attack.py             # regression attack on the exposed DDQ response
python3 ddq_regression_attack_3pxor.py       # same, for the 3PXOR combination
python3 secure_ddq_experiment.py             # exposed response vs. controlled HMAC interface
```

`secure_ddq_experiment.py` rewrites the files in `results/`. Its attacker-accuracy figures for the controlled interface can differ slightly in the decimals from the committed report; they stay near 50% with zero forgeries.

### C1. HMAC testbenches

```sh
iverilog -g2012 -o hmac.vvp rtl/sha256_compress.sv rtl/hmac_sha256_fixed.sv tb/tb_hmac_sha256_fixed.sv && vvp hmac.vvp
iverilog -g2012 -o top.vvp rtl/sha256_compress.sv rtl/hmac_sha256_fixed.sv rtl/secure_ddq_auth_top.sv tb/tb_secure_ddq_auth_top.sv && vvp top.vvp
```

Expected: `PASS tag=f01bcd48741875e8`, `PASS tag=542f093cc0e73f18`, `TEST PASSED - 0 error(s)`. A `sorry: constant selects in always_*` warning from Icarus is harmless.

With Vivado XSim:

```sh
xvlog -sv rtl/sha256_compress.sv rtl/hmac_sha256_fixed.sv tb/tb_hmac_sha256_fixed.sv
xelab tb_hmac_sha256_fixed -s hmac
xsim hmac -R
```

### C2. Vivado project

```sh
vivado -mode batch -source vivado/create_secure_project.tcl -tclargs sim
vivado -mode batch -source vivado/create_secure_project.tcl -tclargs synth
```

`synth` writes `results/utilization.rpt` and `results/timing_summary.rpt` (LUT / FF / timing numbers). For the baseline PUF project only, use `vivado/create_project.tcl`.

### C3. RTL-generated dataset and attack

```sh
iverilog -g2012 -o gen.vvp rtl/sha256_compress.sv rtl/hmac_sha256_fixed.sv rtl/secure_ddq_auth_top.sv tb/tb_generate_auth_dataset.sv
vvp gen.vvp                                                  # about 1.5 minutes, writes 14,000 tags
cp work/secure_vivado/results/rtl_auth_dataset.csv results/  # Windows: copy ... results\
python3 scripts/attack_rtl_tags.py
```

If you see `FAIL could not open RTL dataset output`, run from the repository root and make sure `work/secure_vivado/results/` exists.

### C4. Vivado GUI visuals (run C2 first)

```sh
vivado -mode gui -source vivado/show_secure_simulation.tcl
vivado -mode gui -source vivado/show_secure_circuit.tcl
```

`show_secure_circuit.tcl` prints hard-coded result text, not live numbers.

## Security boundary and limitations

This is a verified proof of concept, not a hardware-security certification. The secure RTL currently receives `root_key_in` from an external key-reconstruction block. A complete FPGA product still needs a real fuzzy extractor/ECC, authenticated helper data, measured PUF entropy and key reconstruction across boards/temperature/voltage/aging, enforced nonce freshness, removal of debug/raw-response paths, and side-channel and fault-injection evaluation.

HMAC, SHA-256, and nonces are established security mechanisms. The project contribution is their controlled integration with the DDQ-APUF architecture and the measured comparison between an exposed learnable response and protected RTL-generated authentication tags.

## Reference
